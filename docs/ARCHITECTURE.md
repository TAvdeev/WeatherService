# Архитектура приложения и объяснение для защиты

## Предметная область

Вариант 1 — «Погода и климат»: получение текущей погоды по названию города. Сущность БД — история успешных запросов погоды. Долгосрочное моделирование климата и прогноз на несколько дней в данном индивидуальном варианте не требуются.

## Ответственность компонентов

| Контейнер | Технологии | Задача |
| --- | --- | --- |
| `frontend` | Nginx, HTML, CSS, JavaScript | Страница пользователя, отображение погоды и истории, проксирование `/api/*` в Backend. |
| `backend` | Python 3.12, FastAPI, psycopg | Валидация запросов, REST API, CRUD в PostgreSQL, обращение к погодному сервису. |
| `db` | PostgreSQL 17 | Таблица запросов, ограничения целостности, индексы, постоянное хранение в volume. |
| `web-service` | Python 3.12, FastAPI, httpx | Поиск города через GeoNames/Open-Meteo, получение погоды через Open-Meteo, приведение ответа к формату приложения. |

Все контейнеры соединены мостовой сетью `weather-net`. Внутри неё адреса `db:5432`, `backend:8000`, `web-service:8001` разрешаются встроенным механизмом Compose. Браузер обращается только к адресу Frontend. Отдельно опубликованы локальные порты 8000 и 8001 для демонстрации API. PostgreSQL на хост не опубликован; управлять им можно через `docker compose exec db psql ...`.

## Путь запроса погоды

1. Пользователь вводит название города и нажимает «Получить погоду».
2. Frontend вызывает `GET /api/cities?q=...`. Nginx передаёт запрос Backend.
3. Backend вызывает `GET http://web-service:8001/cities?q=...`.
4. Погодный сервис вызывает официальный HTTPS API геокодирования Open-Meteo и возвращает возможные города.
5. Пользователь выбирает населённый пункт при нескольких совпадениях. Frontend передаёт `POST /api/weather` с названием и `location_id`.
6. Backend запрашивает `/weather` у отдельного сервиса. Тот по ID получает координаты из официального API, затем запрашивает текущие условия. URL провайдера задаётся конфигурацией; пользователь не может отправить произвольный адрес для скачивания.
7. Backend проверяет формат ответа и выполняет параметризованный `INSERT ... RETURNING *`. Только после успешной фиксации транзакции возвращает `201 Created`.
8. Frontend отображает карточку и сообщает, что запрос сохранён. При уже открытой истории перечитывает её из БД.

При нажатии «Загрузить историю» запрос идёт Frontend → Backend → PostgreSQL и **не требует Open-Meteo**. Получение списка истории и его общего количества выполняется в одной транзакции с согласованным снимком. Каждая запись — отдельный снимок условий в момент запроса, а не изменяемая карточка города.

## REST API Backend

| Метод и путь | Назначение | Успешный ответ |
| --- | --- | --- |
| `GET /` | Обзор Backend со ссылками | HTML, 200 |
| `GET /health` | Проверка доступности таблицы в БД | JSON, 200 |
| `GET /api/cities?q=Москва` | Поиск возможных городов | JSON с `items`, 200 |
| `POST /api/weather` | Получить текущую погоду и создать запись | Объект записи, 201 |
| `GET /api/history?limit=10&offset=0&city=Моск` | Список, поиск, пагинация | `items`, `total`, `limit`, `offset`, 200 |
| `GET /api/history/{id}` | Прочитать одну запись | Объект записи, 200 |
| `PATCH /api/history/{id}` | Изменить заметку | Обновлённая запись, 200 |
| `DELETE /api/history/{id}` | Удалить запись | Без тела, 204 |
| `GET /docs` | Swagger UI | HTML, 200 |
| `GET /openapi.json` | Машиночитаемое описание API | JSON, 200 |

Пример тела получения погоды:

```json
{"city": "Москва", "location_id": 524901}
```

`location_id` необязателен для прямых API-запросов: без него берётся первое совпадение источника. Интерфейс передаёт ID выбранного населённого пункта.

Пример изменения заметки:

```json
{"note": "Погода перед прогулкой"}
```

Пример структуры ответа приведён ниже. Числа иллюстративные, не текущая погода:

```json
{
  "id": 3,
  "requested_city": "Москва",
  "city": "Москва",
  "country": "Россия",
  "region": "Москва",
  "latitude": 55.75,
  "longitude": 37.62,
  "temperature": 8.5,
  "feels_like": 6.2,
  "humidity": 72,
  "wind_speed": 3.1,
  "weather_code": 3,
  "description": "Пасмурно",
  "observed_at": "2026-10-11T09:00:00Z",
  "requested_at": "2026-10-11T09:01:00Z",
  "source": "Open-Meteo",
  "source_url": "https://open-meteo.com/",
  "note": "",
  "is_demo": false
}
```

Ошибки имеют JSON-поле `detail`: 404 — город или запись не найдены; 422 — неверный ввод; 502 — ошибка/неверный ответ погодного сервиса; 503 — БД недоступна или провайдер ограничил запросы; 504 — время ожидания истекло. Frontend показывает понятное сообщение. Ошибка погодного источника не приводит к сохранению нулевой или случайной погоды.

## API погодного веб-сервиса

| Метод и путь | Назначение |
| --- | --- |
| `GET /` | Страница сервиса с источником и документацией. |
| `GET /health` | Готовность самого процесса; не зависит от внешнего интернета. |
| `GET /cities?q=...` | До 8 совпадений городов. |
| `GET /weather?city=...&location_id=...` | Текущие условия в унифицированном формате. |
| `GET /docs`, `GET /openapi.json` | Документация API. |

Исходящие адреса: `https://geocoding-api.open-meteo.com/v1/search`, `/v1/get` и `https://api.open-meteo.com/v1/forecast`. Нужны только исходящие HTTPS-соединения. Авторизация и API-ключ для учебного некоммерческого использования не требуются.

## Схема PostgreSQL

Используется одна таблица `weather_requests`. Для предметной области «история запросов» отдельные таблицы пользователей и городов не нужны: каждая запись сохраняет название и координаты вместе с погодным снимком, чтобы история оставалась самостоятельной.

| Поле | Тип | Значение |
| --- | --- | --- |
| `id` | `BIGINT`, identity, primary key | Автоматический идентификатор записи. |
| `requested_city` | `VARCHAR(100)` | Введённое пользователем название. |
| `city` | `VARCHAR(100)` | Название выбранного города от провайдера. |
| `country` | `VARCHAR(100)` | Страна. |
| `region` | `VARCHAR(150)` | Регион, при отсутствии — пустая строка. |
| `latitude`, `longitude` | `DOUBLE PRECISION` | Координаты выбранного города; ограничения ±90 и ±180. |
| `temperature`, `feels_like` | `DOUBLE PRECISION` | Температура и ощущаемая температура в °C. |
| `humidity` | `INTEGER` | Влажность 0–100 %. |
| `wind_speed` | `DOUBLE PRECISION` | Скорость ветра в м/с, неотрицательная. |
| `weather_code` | `INTEGER` | Код погодных условий по таблице WMO провайдера. |
| `description` | `VARCHAR(100)` | Русское описание условий. |
| `observed_at` | `TIMESTAMPTZ` | Время погодных данных от источника. |
| `requested_at` | `TIMESTAMPTZ` | Время создания запроса; по умолчанию время БД. |
| `source` | `VARCHAR(100)` | Open-Meteo или явная метка учебного примера. |
| `source_url` | `TEXT` | URL источника. |
| `note` | `VARCHAR(500)` | Редактируемая заметка. |
| `is_demo` | `BOOLEAN` | Отличает начальные примеры от настоящих запросов. |

Все поля `NOT NULL`. Индекс по `requested_at DESC, id DESC` помогает сортировке истории; `id` также задаёт стабильный порядок при одинаковом времени. Есть индекс по `city`; поиск по подстроке `ILIKE '%...%'` при большом объёме потребовал бы дополнительного специализированного индекса, для учебной истории он не нужен. Ввод `%` и `_` в фильтре трактуется буквально. Значения запросов передаются в SQL параметрами.

## Инициализация и жизненный цикл

`db/init.sql` монтируется только для чтения в `/docker-entrypoint-initdb.d/01-init.sql`. Стандартный образ PostgreSQL выполняет его при создании новой БД. Внутри одной транзакции создаются таблица, индексы и две учебные записи. Именованный volume расположен в `/var/lib/postgresql/data` внутри контейнера и не удаляется обычной командой `docker compose down`.

Healthcheck БД использует `pg_isready`. Backend дополнительно проверяет наличие таблицы. `depends_on` с условием `service_healthy` задаёт порядок готовности: db и web-service → backend → frontend. Это проверка запуска, а не автоматический ремонт зависимостей при любой дальнейшей ошибке. Приложение обрабатывает сбои БД и провайдера сообщениями; перезапуск завершившихся процессов обеспечивает `restart: unless-stopped`.

Nginx обновляет разрешение имени Backend через встроенный Docker DNS, поэтому пересоздание Backend не требует перезапуска Frontend только ради нового IP. Это стандартная внутренняя сеть Compose; собственный DNS-сервер, ingress, SSL и отдельный reverse-proxy-контейнер не добавляются.

## Короткие ответы для защиты

- **Зачем отдельный web-service, если API уже внешний?** Задание требует четыре контейнера. Наш четвёртый сервис — самостоятельный адаптер предметной области: он знает API провайдера, геокодирование, единицы измерения и коды условий. Backend отвечает за пользовательские операции и БД.
- **Где CRUD?** Create — `POST /api/weather`; Read — история и отдельная запись; Update — заметка; Delete — удаление записи. Все действия выполняет Backend через PostgreSQL.
- **Почему данные переживают удаление контейнера?** Они находятся в именованном volume, который отделён от файловой системы контейнера.
- **Почему нельзя в браузере открыть `http://backend:8000`?** Это имя внутри сети Docker. Пользователь открывает опубликованный порт Frontend, а тот обращается к Backend из контейнерной сети.
- **Как подтверждается реальный источник?** В коде сервиса указаны официальные HTTPS API, интерфейс содержит атрибуцию, запись хранит источник и время данных. Начальные фиктивные записи явно помечены.
- **Почему погода может не измениться при повторном запросе?** Возвращается последнее доступное значение модели. Частота запросов пользователя не определяет частоту обновления метеомодели.
